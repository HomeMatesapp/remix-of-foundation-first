# Clear Routes — Foundation First — Master Build Plan

## 1. Authority and purpose

This file is the **canonical implementation roadmap** for Foundation First. It is subordinate only to:

1. the frozen normative Clear Routes product/architecture specification, and
2. explicit owner-approved architecture corrections.

It exists to prevent scope drift, skipped dependencies, contradictory increment numbering and implementation-by-memory.

The old convergence / "C-number" roadmap is **historical only**. It must not be used to sequence Foundation First. Foundation First uses the fresh-build Increment 0–36 roadmap in §5 of this document.

If repository history, chat summaries or agent recollection conflict with this roadmap, the **current frozen product/architecture specification plus this roadmap govern**, unless a newer explicitly approved architecture decision supersedes them.

## 2. Formal increment gate — binding

**Scope implemented → actual diff inspected → tests pass → architecture contract preserved → no future-scope leakage → increment closed.**

- **Scope implemented** — only the approved increment acceptance criteria are implemented.
- **Actual diff inspected** — implementation is verified from files, schema and diff, not accepted from an agent summary alone.
- **Tests pass** — required tests plus relevant regression suites pass.
- **Architecture contract preserved** — frozen product, ERD, authority, privacy, deterministic-engine and evidence rules remain intact.
- **No future-scope leakage** — no unapproved later-increment tables, features, vocabularies, UI or speculative architecture appear early.
- **Increment closed** — only after all prior checks pass may the next increment start.

If any stage fails, the current increment **remains open** and receives a reconciliation patch. Do not increment the number merely because implementation is mostly done.

Rule: **"Lovable says complete" is evidence to inspect, not proof of closure.**

## 3. July operating boundary — governing execution rule

Routine work may continue sequentially through the already-approved roadmap **without repeated owner approval for every low-risk substep**. Work must **stop for owner decision** at these hard gates:

- production/hosted DB migrations or destructive production changes
- production data deletion or backfill
- material RLS/auth authority changes beyond already-approved scope
- live imports, publishing or scheduled ingestion
- production deployment
- paid/external services, legal or cost commitments
- third-party data sharing
- wholesale merges or destructive history rewrites
- changes to core product promise, participant journey, business model or consequential AI authority
- any genuine architecture contradiction requiring a new owner decision

This operating permission **never** allows skipping an increment gate or expanding an increment's scope.

## 6. Non-negotiable cross-increment architecture rules

- UK first; internationalisation is future.
- One shared Career Decision Engine plus structured versioned Career Packs; a normal new career must not require a new software engine.
- The canonical immutable Career Pack document is the single source of truth; DB projections are deterministic projections only.
- The four protected assessment judgement states remain exact unless the owner explicitly approves a breaking architecture change.
- Decision state is separate from assessment judgement.
- Eligibility and practical fit are separate.
- Unknown is not unmet.
- Judgement strength must never exceed evidence strength.
- AI may interpret, research and propose but may not secretly determine eligibility or publish consequential truth.
- Automatic assembly, not automatic invention.
- Postcode and local realism are core; absence of a current vacancy is not route impossibility.
- Institution-private adviser-origin progression must not leak across institutions; participant/system shared progression remains separately governed.
- Historical inputs, results and content must be reconstructable from immutable versioned references and hashes.
- PostGIS is the locked geographic implementation; no silent Haversine fallback.
- Do not create speculative fields, enums or tables early "for later".
